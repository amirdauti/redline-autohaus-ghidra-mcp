# Decompiler, data-flow and comparison tools

These tools operate on the active program through native Ghidra APIs. They require `expected_program_id`, observe analysis/context guards, and do not commit decompiler or emulator results to program bytes or metadata. Addresses are space-qualified hexadecimal CPU addresses, not file offsets. Results exceeding4MiB of serialized UTF-8 return a recoverable error; reduce page, node or batch limits. Read-only does not mean that an emulator result describes real hardware.

| Tool | Contract and limits |
| --- | --- |
| `get_high_pcode` | Decompiler SSA for the function containing `address`. `offset` defaults to0, `limit` to128 (max512). Returns operation sequence address/time, inputs/output, varnode storage, high variable names/types, total count and a SHA-256 `snapshot_id`. At most20000 operations/65536 varnodes per function; decompilation10seconds and bounded traversal. |
| `trace_data_flow` | Requires a fresh `expected_snapshot_id`, function `address`, `operation_address`, `operation_time`, and `operand_index` (-1 for output;0..31 for input). `direction` is forward/backward. Defaults:4 edges deep/64 nodes; maximum8/128,512 edges. Follows SSA def-use links within one function. Calls, memory loads/stores and indirect side effects are explicit terminal boundaries. No interprocedural, alias, control-dependency or full taint analysis. |
| `batch_decompile` |1..8 mapped addresses; each resolves its containing function independently. Four-second native timeout per function,40-second batch budget. Per-item success/error, C capped at65536 UTF-16 units and explicit truncation. A mapped address outside any function returns a per-item error. |
| `batch_references` |1..32 mapped addresses, direction to/from, `limit_per_address` default100/max200,10-second traversal. References come from the existing Ghidra database; absence does not establish lack of runtime use. |
| `search_decompiled_code` | Literal case-sensitive text (1..256 characters), function window default4/max8. Optional exclusive `start_after` function-entry address. Returns all per-function outcomes, matches with offsets/line/snippets, and a resume cursor. Searches only the returned capped C text; truncation/errors are explicit, never claimed to be a complete-program search.20 matches per function. |
| `get_function_fingerprint` | Normalized mnemonic, operand-kind and explicit register sequence; max instructions defaults1024/max4096. SHA-256 includes language/compiler IDs. Constants and addresses are omitted. Truncated fingerprints represent only prefixes and are marked. |
| `compare_functions` | Same active program, `address` and `other_address`. Returns both fingerprints, normalized-sequence equality only when both are complete, and normalized token multiset Jaccard score0..1. Equal fingerprints/scores do **not** prove semantic equivalence; different immediates may intentionally match. |
| `find_similar_functions` | Ranks only a bounded listing window. Exclusive `start_after`; default25/max100 functions,10seconds,10000 candidate instructions; top10/default, max25 results. Per-function instruction cap as above. Reports scan count, failures, resume cursor and `ranking_scope=scanned_window`. Scores are candidate hints, not function identification. |
| `emulate_function` | Isolated native emulator, existing function entry and explicit existing instruction `stop_address` in default memory. At most10000 steps/5seconds. Inputs: up to32 non-context registers of at most64bits,16 mapped memory regions/8192bytes total. Output:1..16 registers and up to16 memory regions/8192bytes. Stops before executing the stop instruction. No state is copied back to the program. |

SSA identifiers belong to a decompilation snapshot. Tracing rejects a changed snapshot instead of guessing that the same variable or sequence number still means the same thing. Names/types are decompiler inferences and may depend on existing analysis and signatures. Repeated cursor calls traverse the current listing, not a frozen database snapshot; edits may alter later results. Batch/search failures and capped C text must be considered when interpreting missing matches.

The emulator has no operating system, peripherals, timing model or automatic function ABI setup. Supply needed registers and initialized stack/RAM yourself. Uninitialized reads and unsupported p-code/user operations are failures, not synthesized hardware behavior. `outcome` distinguishes reaching the stop address, step/time limits and native errors. `steps` counts attempted complete-instruction steps; a cancellation can stop within a native step. Explicit memory inputs modify only the emulator overlay, including when their addresses overlap source bytes. Only declared output ranges/registers are returned. Unreadable outputs contain null value/bytes and a per-item error; they are never reported as zero-filled success. PC is set from the entry address; supplying PC or overlapping register inputs is rejected.

Native acceptance uses generated x86 code for SSA arithmetic, calls, scalar constants that normalize equally, bounded literal search, register arithmetic and private memory writes. `FlowTriCoreFixtureMain` independently assembles, disassembles and emulates the same generated fixture with both `tricore:LE:32:tc29x` and `tricore:LE:32:default`, compiler `default`: bytes `82720b32002000000090` at `ram:80000000`, inputs `d3=5` and `PSW=0`, stopping before `ram:80000006`. Two instructions compute `d2=12`; byte preservation is checked. The helper accepts installation directory, an absent report path, and an optional language ID limited to those two variants (default:TC29x). It uses a disposable in-memory program; this does not establish support for importing TC29x processor default memory blocks through the single-block raw importer. This establishes the fixture, not an entire ECU or device model. `EmulatorHelper` is a native Ghidra12.1.3 API marked for future removal; unsupported languages or operations return explicit errors and will need separate acceptance as Ghidra evolves.
